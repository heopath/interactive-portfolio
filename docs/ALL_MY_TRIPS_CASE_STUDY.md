## 팀 전체 기능과 개인 참여 범위

팀 프로젝트에는 여행 일정 생성·편집, AI 일정 추천과 RAG 여행 가이드, 항공·숙소 검색 및 외부 예약 연결, 티켓 예약·모의 결제·검표, 상담·관리자 기능과 여행 기록 기능이 포함됩니다. 이는 팀 전체의 구현 범위이며 개인이 모두 독자 구현했다는 의미가 아닙니다.

개인 참여 내용은 다음과 같습니다.

- 팀장으로 일정·Issue·PR 관리 및 협업 진행
- Java·Spring Boot 백엔드와 티켓 예약 관련 기능 구현 참여
- AWS EC2·RDS 배포 및 GitHub Actions 빌드·배포 흐름 구성
- Oracle Cloud로 애플리케이션과 PostgreSQL 데이터를 이관
- 앱·DB 서버 분리, Nginx·HTTPS 설정을 통한 포트폴리오 서비스 공개

구현 과정에서 AI 도구의 도움을 받았습니다. 기술을 적용한 경험과 독자적으로 설계·설명할 수 있는 역량은 구분하며, 사용한 코드의 요청 처리·SQL·대기열 동작을 다시 학습하고 있습니다.

## 사례 1 — 한정 재고의 예약 처리

### 다룬 문제

여러 요청이 동시에 같은 재고를 조회하면 남은 수량보다 많은 예약이 생성될 수 있습니다. 대기열의 입장 관리와 실제 DB 재고 처리를 구분해야 하는 문제였습니다.

### 프로젝트에 적용한 방식

- Redis Sorted Set·Lua 기반 대기열: 등록 순서와 입장 상태 관리
- MyBatis Mapper XML과 Spring 트랜잭션: 예약·재고 SQL 처리
- PostgreSQL 행 잠금·조건부 UPDATE: 같은 재고를 처리하는 요청 조정 및 잔여 수량 조건 확인
- Spring Data JPA: Entity·Repository 기반 CRUD와 연관관계 매핑에 사용; 위 재고 제어를 JPA 구현으로 설명하지 않음

대기열을 통과했다고 예약 성공이 확정되는 것은 아닙니다. DB 처리 시점에 재고가 소진되면 예약 요청은 거절됩니다.

### 저장소에 남긴 로컬 검증 기록

[예약 대기열 k6 결과와 DB 교차 확인 기록](https://github.com/heopath/TravelGuide-Project-Team1/blob/main/docs/qa/booking-queue-load-test-results.md)을 근거로 정리했습니다. 아래는 해당 문서의 **2026.08.14 로컬 실행 기록**이며, 현재 Oracle Cloud 환경에서 새로 측정한 결과가 아닙니다.

- 환경: 로컬 프로필 애플리케이션, PostgreSQL 16.14·Redis 7 컨테이너, k6
- 조건: 가상 사용자 30명(30 VU), 사용자별 1회 예약 시도, 티켓 재고 10개
- 기록된 결과: 예약 성공 10건, 재고 소진 처리 20건
- DB 교차 확인: 예약 10건·서로 다른 사용자 10명·예약 수량 10개·총 재고 10개
- 같은 날 후속 실행에서는 예상한 재고 소진 응답(HTTP 409)을 정상 업무 결과로 분류했으므로, 기록의 요청 실패율 0%는 모든 요청의 예약 성공을 뜻하지 않음

이 결과는 특정 시나리오에서의 예약·재고 일치 확인 자료입니다. 최대 처리량, 상용 서비스 안정성 또는 모든 동시성 상황의 안전성을 보장하는 수치로 사용하지 않습니다. 다른 날짜의 후속 실행과 시나리오는 원문에서 구분해 확인할 수 있습니다.

## 사례 2 — AWS 배포 후 Oracle Cloud 이관

### 목적

교육 과정에서 만든 서비스를 수료 이후에도 포트폴리오로 보여주기 위해, 기존 AWS 배포 경험을 바탕으로 다른 클라우드에 실행 환경을 옮겼습니다.

### 진행한 작업

1. AWS EC2·RDS에 애플리케이션과 DB를 배포하고 GitHub Actions 기반 빌드·배포 흐름을 구성했습니다.
2. Oracle Cloud A1 생성 시 용량 부족을 겪은 뒤 E2 Micro 환경으로 구성을 진행했습니다.
3. 애플리케이션과 PostgreSQL 데이터를 옮기고 앱·DB 서버를 분리했습니다.
4. Spring Boot·PostgreSQL·Redis 실행 환경과 Nginx·HTTPS를 설정해 포트폴리오 확인용으로 공개했습니다.

이관 경험은 기능 구현뿐 아니라 배포 설정·데이터 이전·서비스 연결을 함께 다뤘다는 점에서 의미가 있습니다. 다만 저메모리 시연 환경이며, 대규모 트래픽 운영이나 무중단 이관을 수행했다는 의미는 아닙니다. 현재 비용·가용성과 외부 API 동작은 실제 계정 및 서비스 상태를 별도로 확인해야 합니다.

## 회고와 보완할 학습

웹페이지 구현을 마치는 것과 서버에 배포해 접근 가능하게 만드는 일이 다르다는 점을 경험했습니다. 또한 Redis 대기열과 DB 재고 처리가 서로 다른 역할을 한다는 점, 테스트 결과에는 실행 조건과 기대 응답을 함께 남겨야 한다는 점을 배웠습니다.

앞으로는 다음 내용을 코드와 함께 설명하고 직접 수정하는 연습을 이어가고자 합니다.

- 요청이 Controller·Service·Mapper를 거쳐 DB에 반영되는 과정
- 트랜잭션 경계, 행 잠금과 조건부 UPDATE의 역할 및 실패 시 처리
- Redis 대기열의 순서·입장·만료 처리
- 환경변수, 로그, 프로세스, Nginx 설정을 통한 배포 문제 확인

서버 테스트 총개수·화면 테스트 총개수·배포 소요시간처럼 시점과 환경에 따라 달라지는 기록은 현재 성과로 단정해 싣지 않았습니다. 프로젝트 적용 경험과 현재 학습 중인 범위를 구분해 소개합니다.
